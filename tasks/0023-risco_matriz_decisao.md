# Risco real na matriz de decisão + enforcement das permissões de escrita

**Status:** concluído (infraestrutura genérica — as tools de escrita que a consomem continuam em tarefas separadas)
**Prioridade:** P2
**Seção no ROADMAP:** 3. Camada de IA — MVP 2 e além

Hoje `agent/decisao.ts` sempre assume risco "baixo" e `registrarDecisao` grava `risco: 'baixo'` fixo (não há tool de escrita). Quando o MVP 2 chegar, a matriz precisa considerar risco E consumir os campos de permissão que já existem em `ia_permissoes` (migration `0010_ia_permissoes.sql`) mas hoje só validam `permitido`: `exige_confirmacao_humana`, `valor_maximo_sem_handoff`, `condicoes_json.status_permitidos`, `campos_permitidos` — nenhum deles é lido em código.

**Atualização (tarefa 0055):** `exige_confirmacao_humana`/`valor_maximo_sem_handoff` já deixaram de ser letra morta — a tool `criar_pedido` (`apps/ai-orchestrator/src/tools/pedido.ts`) já lê os dois via `avaliarRiscoCriarPedido` (`packages/shared/src/pedido-criacao.ts`) e o orquestrador já força handoff quando o gate bloqueia (veto determinístico em `agent/orquestrador.ts`, mesmo padrão do guard de prompt injection). Essa é uma implementação **pontual, só pra `criar_pedido`** — não é a matriz de decisão genérica que esta tarefa (0023) ainda precisa entregar pras próximas tools de escrita (`adicionar_item`, `alterar_item`, `cancelar_pedido` — tarefas 0057/0058, ainda pendentes) e pra `condicoes_json.status_permitidos`/`campos_permitidos`, que continuam sem nenhum código lendo. Quando 0023 for implementada de verdade, considerar generalizar `avaliarRiscoCriarPedido` em vez de reimplementar o gate por tool.

**Lacuna real, documentada conscientemente:** sem `exige_confirmacao_humana`/`valor_maximo_sem_handoff` configurados pela empresa, `criar_pedido` roda de forma permissiva (sem limite de valor) — mesmo padrão de "ausência = permissivo" já usado em `comportamento_json`. Isso é aceitável enquanto o volume é baixo (empresas piloto), mas é exatamente a lacuna que uma matriz de risco real (esta tarefa) deveria fechar de forma mais robusta antes de qualquer empresa real depender disso em produção com volume alto.

**Implementado:**
- `packages/shared/src/risco-acao.ts` (novo) — `avaliarRiscoAcao()` generaliza `avaliarRiscoCriarPedido()` pra qualquer tool de escrita: além de `exige_confirmacao_humana`/`valor_maximo_sem_handoff` (já existiam, só pra `criar_pedido`), agora também lê `condicoes_json.status_permitidos` (bloqueia se o status atual do pedido não estiver na lista permitida — cobre o caso de `cancelar_pedido` da tarefa 0058: só cancelar enquanto ainda `aberto`/`confirmado`) — as duas colunas (`condicoes_json`, `campos_permitidos`) que existiam desde a migration 0010 e nunca tinham nenhum código lendo. `valorFinanceiro`/`statusAtual` são parâmetros opcionais — uma tool sem esse conceito simplesmente não os passa. Também `filtrarCamposPermitidos()`, enforcement genérico de `campos_permitidos` (pra `atualizar_cliente`/`alterar_item`, tarefas 0059/0057).
- `packages/shared/src/pedido-criacao.ts` — `avaliarRiscoCriarPedido` agora é um wrapper fino sobre `avaliarRiscoAcao` (mesma assinatura/comportamento, sem quebrar `tools/pedido.ts` nem os testes existentes).
- `apps/ai-orchestrator/src/tools/registry.ts` — `getRiscoFerramenta(nome)`, lê `ToolDefinicao.risco` (existia em cada tool desde sempre, nunca era consultado).
- `apps/ai-orchestrator/src/agent/orquestrador.ts` — `calcularRiscoMaximo(evidencias)` substitui o `risco: "baixo"` fixo em `registrarDecisao` (agora `ia_decisoes.risco` reflete o risco real da rodada, ex.: `"alto"` quando `criar_pedido` foi chamado); o veto determinístico que antes só cobria `criar_pedido` (`bloqueioCriarPedido`) foi generalizado pra `bloqueioAcaoAltoRisco` — qualquer tool futura que devolva `{erro:"confirmacao_humana_necessaria", motivo, ...}` via `avaliarRiscoAcao` é coberta automaticamente, sem precisar editar este arquivo de novo a cada tool nova.
- 11 novos casos determinísticos no gabarito (`apps/ai-orchestrator/src/eval/deterministicos.ts`) cobrindo a nova checagem de status, `filtrarCamposPermitidos`, regressão de `avaliarRiscoCriarPedido`, e `calcularRiscoMaximo`. Gabarito completo: 77/77.

**Fora do escopo desta tarefa (continuam tarefas separadas):** implementar os executores de `adicionar_item`/`alterar_item` (0057), `cancelar_pedido` (0058) e `atualizar_cliente` (0059) — esta tarefa só entrega a infraestrutura genérica de risco/permissão que essas tools vão consumir, sem reimplementar o gate cada uma por conta própria.
